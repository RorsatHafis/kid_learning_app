### How to maintain this document

1. Update it at the end of every battle, in the same session.
2. Record only evidence that was actually produced; use the `CLAUDE.md` §6 levels exactly.
   A level observed in an earlier battle and not re-run is labelled "at battle time".
3. Move items between statuses only with evidence. Never mark an area complete because
   code exists or compiles.
4. Keep finding IDs stable (L*, N*, 3R.*, TD-*, PD-*); never reuse an ID.

### Status legend

| Code | Meaning |
|---|---|
| **VC** | VERIFIED COMPLETE — behavior correct for its accepted scope, with automated tests and runtime evidence |
| **PV** | IMPLEMENTED BUT PARTIALLY VERIFIED — works as far as verified; a required level of evidence is missing |

## Headline

**Working mode changed (2026-09-25):** the master production build directive replaces
battle-by-battle findings with product waves (W1 child + parent, W2 teacher + school, W3
admin + Content Studio, W4 identity + security, W5 subscription, W6 release). Finding IDs
stay stable; wave slices are recorded in the register below like battles.

**BACKEND FOUNDATION: integrity baseline established — not production-complete.**
The core learning loop (content → path → attempt → evidence → mastery → adaptive/review →
parent insight) is server-authoritative end to end since 5D, and authentication/session
state, configuration and content versioning have each been hardened and verified to the
levels below. The content tenancy boundary (N7) is enforced since W1.1. Open items
remain in learning-loop policy (PD-11, PD-12, OD-10) and security hardening (rate limiting).

**FULL BOOKEYOND KID PRODUCT: NOT COMPLETE.**
W1.1 delivered the first real child and parent learning experience (journey, play, feedback,
Learning Buddy, evidence-grounded parent overview) — BROWSER VERIFIED on desktop and mobile.
W3.1 delivered the Admin console and Content Studio: an administrator can author a curriculum
from nothing (subject → skills → objectives → questions → activities → curriculum) with
server-side publish validation, and a family's child can learn from it — BROWSER VERIFIED end to
end. Still unbuilt or partial: the canonical content itself (educator-authored, PD-15 — the tool
now exists), Khmer UI (PD-14), goals, school domain authorization (PD-01), principal console,
localization/media in the Studio, identity verification, subscription and deployment. Do not
describe the product as complete.

### PD-01 — family-granted school access (adopted 2026-09-29; built in X4)

**Status:** adopted under the owner's delegation (PLATFORM-EXPANSION.md §4) with the recommended answers to (a)–(d), and
built in X4. The original proposal is kept below as the record of the decision.

**RESEARCH FINDING.** Products where the family owns the child's profile link it to a school through a
parent-entered code rather than school-side enrolment: ClassDojo (a class code or invite the parent accepts),
Seesaw (a "Home Learning Code" the teacher hands out). Google Classroom differs because the school owns the account —
not our model, since Bookeyond children belong to families (PD-05, directive §14.1).

**ENGINEERING RECOMMENDATION** — four relationships, each explicit (CLAUDE.md §15):

1. **Class join code** (school side): a principal or the class's teacher generates a short-lived code (e.g. 8
   characters, 14 days, revocable, rate-limited redemption). The code only *identifies* a class; it grants nothing.
2. **School access grant** (family side, new table `school_child_access`): a parent of the child enters the code on the
   child's page, sees the school, the class and **exactly what the school will see**, and grants. One row per
   (child, school): `ACTIVE` → `REVOKED`, `granted_by`, timestamps, audited. Only a family OWNER/parent of that child can
   grant or revoke — never school staff, never an admin on the family's behalf.
3. **Class enrolment** follows from the grant (the existing `class_enrollments`, now always backed by an ACTIVE grant —
   this also resolves TD-14).
4. **Teacher access** stays assignment-scoped (W2.1): a teacher sees a child only while the child is enrolled in a
   class they are assigned to *and* the grant is ACTIVE.

**What the school sees** (recommended, least privilege, §10): the child's display name, and evidence/progress **only
for curricula the school assigned**. Family-chosen curricula, parent insights and anything else the family did at home
stay private. **Revocation** (any time, by the parent): access ends immediately; enrolments end; the child keeps every
piece of their own learning history (evidence is never deleted because access changed).

**Decisions needed from the owner (PRODUCT DECISION):**
- (a) Join mechanism: parent-entered class code (recommended) / school emails an invitation to the parent / both.
- (b) School visibility: only school-assigned learning (recommended) / everything the child does.
- (c) Whether a confirmed email is required before granting (PD-22 — recommended: yes).
- (d) Anything a school must *not* be able to do even with access (e.g. change the child's name — recommended: read-only).
